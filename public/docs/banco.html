🧹 Limpeza administrativa

limpar_dados_antigos() → SECURITY DEFINER → EXECUTE: postgres / service_role → padrão de retenção: 45 dias
A rotina única de limpeza remove somente registros antigos de generated_games, historico_palpites e transacoes. A tabela usuarios não é apagada nem alterada por essa rotina.

🔧 Funções técnicas

set_app_user_id(user_id text) → SECURITY DEFINER → EXECUTE: postgres / service_role
Exceção preservada: update_updated_at_column() continua com EXECUTE público porque é uma função de trigger. Ela é usada pelo trigger trg_users_updated_at da tabela public.users. Não é uma RPC de negócio.

🧹 Política de retenção de dados

Regra atual

45 dias
↓
generated_games.created_at → limpar registros antigos
historico_palpites.data → limpar registros antigos
transacoes.created_at → limpar registros antigos

A limpeza é global e baseada na idade do registro, não na data de login do usuário.

Conta do usuário

Preservar: limpar_dados_antigos() não executa DELETE em usuarios. Créditos, status PRO, e-mail, UID e cadastro permanecem.

Rotinas antigas removidas

limpar_dados_antigos(user_uid text) → removida limpar_historico_antigo() → removida limpar_historico_usuario(user_uid text) → removida Rotina oficial: limpar_dados_antigos() → 45 dias
Automação: a rotina oficial de 45 dias está criada e protegida, mas a execução automática semanal aos domingos ainda é uma pendência.

Pendência 1 — atualização imediata após pagamento:
o banco é atualizado, mas a interface não reflete imediatamente os novos créditos/PRO. Atualmente, sair e entrar novamente atualiza os dados. O problema identificado é de refresh/sincronização do estado da aplicação, não do RLS.
